# Prompt Intelligence: Architecture Design

*A design for the third architectural pillar alongside Provider Management
([01-provider-management-v2.md](01-provider-management-v2.md)) and Memory Management.
This is a design document — no code changes accompany it, no runtime prompts
are generated by it, and it does not depend on any static per-provider prompt
file. Four internal research memos on per-provider prompting philosophy were
used as reference input; none of their text is reproduced here — only the
architectural principles they imply.*

**Confirmed dead end, not to be resurrected:** an earlier `PromptAdaptationEngine`
(`velune/context/prompt_adaptation.py`, 8 per-family templates keyed off
`ModelFamily`) was deleted in the context-system overhaul and never restored.
Its design — a `Protocol`-based template per family with a `StandardAPITemplate`
fallback — was sound and is reused conceptually below (§3, §4), but the code
itself is gone; nothing in this design assumes it still exists.

**Confirmed orphaned duplicate, out of scope:** `velune/cognition/agents/{coder,
planner,reviewer}.py` hardcodes its own static system prompts and bypasses
`cognition/prompts` entirely. Nothing imports this package outside its own
`__init__.py`. Per the guardrail against opportunistic fixes, this is flagged
here and left untouched — a candidate for a separate deletion task, not folded
into this migration.

### The actual gaps

1. **No provider-aware rendering at all.** The exact same assembled string is
   sent to every provider and every model family. Claude, GPT, and Gemini
   receive identical structure, delimiters, and ordering today.
2. **No task-template abstraction independent of the council seats.**
   `cognition/prompts` covers council roles (planner/coder/reviewer/...) but
   there is no reusable, provider-independent template for task *kinds*
   (debugging, code review, architecture, research, terminal execution) that
   the REPL's direct-chat path or future surfaces could share.
3. **No user-project convention ingestion.** There is no equivalent of
   "read the user's own CLAUDE.md / README / architecture docs and fold them
   into context" — `ProjectType` classification exists, but no file-based
   convention loader does.
4. **No validation layer.** Nothing today detects duplicated instructions,
   conflicting constraints, or an over-budget *combined* prompt+tools+context
   payload before it goes out the wire.
5. **No token-optimization strategy beyond section trimming.** `ContextAssembler`
   trims by section; there is no cross-section deduplication or provider-specific
   budget split (e.g., a family with a small system-prompt ceiling, mirrored
   from the deleted engine's Phi 512-token cap).

Everything below is designed to close these five gaps **by extending the
patterns already proven in this codebase** — canonical form + boundary
translation (tools), content/code separation (`_baseline`/`_premium`), and
section/budget assembly (`ContextAssembler`) — not by replacing them.

## 1. Purpose

Prompt Intelligence is the subsystem responsible for **compiling** — not
storing — the final instructions sent to a model. It takes the same abstract
task intent, the same repository/memory/tool context, and the same user
request, and renders them differently depending on which provider and model
family will receive them. No static per-provider prompt file exists anywhere
in the system; provider behavior is expressed as declarative capability
profiles, and rendering is a pure function from *(intent, context, profile)*
to *(final message list)*.

It sits downstream of Provider Management (which resolves *which* model
answers a turn) and Memory Management (which resolves *what* the model should
know), and upstream of the wire-format adapters in `velune/providers/adapters/`
(which resolve *how* bytes reach the API).

## 2. Responsibilities

- Own the **Prompt IR** (intermediate representation): a typed, structured
  representation of a prompt's sections, independent of any provider's text
  format.
- Own **Provider Profiles**: declarative capability/preference descriptors per
  model family (delimiter style, context ordering, planning verbosity, system
  token ceiling, prompt-caching support).
- Own **Provider Renderers**: pure IR → final-text transforms, one per family
  (plus a Generic fallback), implementing the ordering/format/delimiter rules
  a profile declares.
- Own the **Task Template Registry**: reusable, provider-independent templates
  for task kinds (coding, debugging, planning, review, refactoring,
  documentation, architecture, research, terminal execution).
- Own the **Context Builder**: the adapter that packages `ContextAssembler`
  output plus new sources (user-project CLAUDE.md-equivalent, README,
  architecture docs) into IR Context nodes, without altering
  `ContextAssembler`'s ordering/budget/trust guarantees.
- Own **Prompt Validation**: conflict, duplication, and overflow detection
  over the assembled IR, before any renderer runs.
- Own **Token Optimization**: deduplication, adaptive truncation, and
  provider-specific budget splitting, delegated to and consistent with
  `ContextBudget`, not a parallel budget system.
- Explicitly **not** responsible for: choosing which model answers a turn
  (Provider Management), retrieving/ranking memory (Memory Management),
  wire-format translation of the final messages (existing adapter layer),
  or tool *execution* (existing tool-loop/permission machinery).

## 3. Design Philosophy

### 3.1 The core tenet: separate intent from rendering

The single architectural idea underneath everything else — and the one
explicitly named in the "generic" research memo — is that **the same abstract
task must never be hand-authored once per provider**. Instead:

```
TaskIntent + ContextBundle + ToolContext  →  PromptIR  →  Renderer(family)  →  final messages
```

The IR is the only thing task templates, context, and constraints are
expressed in. Providers differ only in *how the renderer reads the IR*, never
in *what the IR contains*. This is exactly the canonical-form-plus-boundary-
translation pattern already proven for tool schemas in this codebase
(`ToolRegistry.list_tool_schemas()` → per-adapter `_translate_tool`) — this
design generalizes that pattern one layer up, to prompts.

### 3.2 Principles extracted from the four provider research memos, and where they land

| Principle (source) | Architectural consequence |
|---|---|
| Claude: XML boundaries for distinct content kinds; negative tool guidance; stable rules early, volatile content late; plan/execute separation; externalize memory into structured state | `AnthropicRenderer` wraps IR sections in semantically-named XML tags; `ProviderProfile.context_ordering = STABLE_FIRST`; task templates carry explicit "when to use / when not" tool narrative fields |
| OpenAI/GPT: Markdown hierarchy (Role→Objectives→Constraints→Workflow→Tools→Output); concise, behavioral, numbered constraints; no redundancy | `OpenAIRenderer` emits `## Role` / `## Constraints` headers in that fixed order; `PromptValidator` actively rejects/collapses redundant constraint duplication before render |
| Gemini: context-before-instruction; "anchor" transition phrase after long context; staged reasoning protocol; many-shot pattern mimicry | `ProviderProfile.context_ordering = CONTEXT_FIRST`; `GeminiRenderer` inserts an anchor sentence between the context block and the current request |
| Generic: capability profiles over hand-written prompts; one compiler renders one abstract task per profile | This is the whole architecture (§3.1) — not one renderer feature but the reason renderers exist at all |

None of the four memos are read at runtime. Their content was extracted once,
during this design pass, into the declarative `ProviderProfile` dataclasses
and `ProviderRenderer` classes below — both checked-in, reviewed, unit-tested
code, not text blobs.

### 3.3 Reuse, don't replace

- `ContextAssembler`'s section ordering, trust-based trimming, and budget
  enforcement (§0) are correct and already tested — the Context Builder wraps
  it and adds new sources; it does not fork or reimplement it.
- `cognition/prompts` (`_baseline`/`_premium`) already solves content/code
  separation for prompt text — the Task Template Registry treats those
  strings as IR-node *content providers* (a template's `role_fragment` may
  literally be `get_prompt(COUNCIL_CODER)`), not a system to route around.
- `ModelFamily`/`detect_family` remains the single family-detection function.
  Prompt Intelligence adds a `family → ProviderProfile` mapping; it does not
  add a second detector.

### 3.4 Alternatives considered

| Option | Verdict | Why |
|---|---|---|
| **A. Do nothing** — keep static `_baseline`/`_premium` strings as-is | Rejected | Doesn't scale past today's 3-ish provider families the user actually cares about optimizing for; contradicts the explicit brief; leaves gaps 1–5 (§0) open |
| **B. Fork `ContextAssembler`** into per-provider assemblers | Rejected | Duplicates already-correct budget/trim logic N times; violates §3.3; combinatorial maintenance as providers grow |
| **C. Push rendering into each of the ~20 provider adapters** | Rejected | Adapters are wire-format translators today (a narrow, well-tested responsibility) — folding prompt-authoring into 20 files instead of ~4 family-keyed renderers duplicates logic and makes adapters harder to test in isolation |
| **D. Insert a provider-agnostic IR + family-keyed renderer layer** between `ContextAssembler` output and `InferenceRequest` construction | **Chosen** | Extends the exact pattern already proven for tool schemas; reuses `ContextAssembler` and `cognition/prompts` unchanged as inputs; adding a provider is one profile + optional renderer, not a new assembler |

## 4. Core Components

```text
TaskIntent            What the user/system is trying to do (task kind +
                       the current request text). Reuses the existing
                       IntentClassifier already invoked in prompt_context.py
                       — not a second classifier. Does NOT carry an urgency/
                       tier field: IntentClassifier and the Council's
                       classify_task_tier are two independent, uncorrelated
                       classifiers today (see 03-cognitive-architecture.md §0.2)
                       — TaskIntent should adopt a unified urgency signal
                       once that document's Executive Brain unification
                       ships, not before.

PromptIR               Typed prompt intermediate representation: Role,
                       Objectives, Constraints, Context (nested: repository,
                       memory, diagnostics, conventions), ToolContext,
                       Workflow/Planning, Examples, OutputContract.

ProviderProfile         Declarative capability/preference descriptor per
                        model family: delimiter_style, context_ordering,
                        planning_style, max_system_tokens,
                        supports_prompt_caching, verbosity_bias,
                        anchor_phrase (Gemini-style), tool_narrative_style.

ProviderRenderer        ABC: render(ir: PromptIR, profile: ProviderProfile)
                         -> RenderedPrompt. One concrete subclass per family
                         that needs bespoke structure; families with no
                         bespoke need just get a profile, no renderer
                         subclass (falls through to GenericRenderer).

TaskTemplateRegistry      Maps task kind -> TaskTemplate (provider-independent
                          IR-node factory). Seeded from cognition/prompts
                          content, not a rewrite of it.

ContextBuilder             Wraps ContextAssembler.assemble() + new sources
                            (user CLAUDE.md-equivalent, README, architecture
                            docs) into PromptIR Context nodes. Delegates
                            budget/trust/ordering to ContextAssembler; adds
                            nothing of its own on that front.

PromptValidator              Runs over the assembled IR before rendering:
                             duplicate-instruction detection, conflicting-
                             constraint detection (explicit precedence,
                             §14), malformed-section detection, provider/
                             capability-mismatch detection (e.g. IR requests
                             JSON mode from a profile that doesn't support it).

TokenOptimizer                Deduplication + adaptive truncation +
                              provider-specific budget split. Delegates to
                              ContextBudget for the actual numbers; adds only
                              the per-family ceiling (e.g. a small-context
                              family's tighter system-prompt cap).

PromptCompiler                 Orchestrator: TaskIntent + ContextBundle +
                               ToolContext -> TaskTemplateRegistry lookup ->
                               ContextBuilder -> constraint resolution ->
                               PromptValidator -> ProviderRenderer selection
                               -> RenderedPrompt -> CompiledPrompt (messages
                               + compilation report).

FamilyProfileRegistry            The new family -> ProviderProfile mapping.
                                 Built on the existing detect_family(), not a
                                 replacement for it.
```

## 10. Prompt Compilation Pipeline

1. **Intent resolution** — reuse the existing `IntentClassifier` output; wrap
   it as `TaskIntent` (no new classification logic).
2. **Template resolution** — `TaskTemplateRegistry.get(intent.kind)` returns a
   provider-independent `TaskTemplate`; its `role_fragment`/`constraint_set`
   draw on `cognition/prompts` content where a council-equivalent role exists.
3. **Context assembly** — `ContextBuilder` wraps `ContextAssembler.assemble()`
   output plus new sources (§12) as `IRContextNode[]`, preserving section
   ordering, trust scores, and budget guarantees unchanged.
4. **Constraint resolution** — merge template constraints, explicit
   user-request constraints, and provider-default constraints under the fixed
   precedence in §6/§14; duplicates collapsed here, before validation.
5. **Token optimization** — `TokenOptimizer` dedupes cross-section repeats and
   fits the IR to the per-family budget (delegating to `ContextBudget` for the
   numeric allocation).
6. **Validation** — `PromptValidator` runs conflict/duplication/overflow/
   capability-mismatch checks; failures are resolved per §14, never silently
   dropped without a `CompilationReport` flag.
7. **Renderer selection** — `FamilyProfileRegistry` resolves `ModelFamily` →
   `ProviderProfile`; `GenericRenderer` is the universal fallback.
8. **Rendering** — the selected `ProviderRenderer` turns the validated IR into
   a `RenderedPrompt` (messages + cache hints).
9. **Reporting** — a `CompilationReport` (template used, family, renderer,
   validation outcome, budget status, IR hash) travels alongside the rendered
   prompt for observability (§15, §17) — it is never silently discarded.

## 11. Provider Rendering Pipeline

Each `ProviderRenderer` implements the same four steps, differing only in
*how*, per its `ProviderProfile`:

1. **Order sections** — per `context_ordering`: `STABLE_FIRST` (Claude: role/
   constraints first, volatile context last), `CONTEXT_FIRST` (Gemini: full
   context before the instruction, with an anchor phrase transition),
   `ROLE_TASK_CONTEXT` (OpenAI: fixed Role→Objectives→Constraints→Workflow→
   Tools→Output hierarchy).
2. **Apply delimiter style** — `XML` (semantically-named tags per section,
   Claude), `MARKDOWN` (`##` headers, OpenAI), `PLAIN` (Generic fallback for
   unclassified/local families, mirroring the deleted engine's
   `StandardAPITemplate` behavior).
3. **Apply planning style** — `EXPLICIT_PHASES` inserts a numbered plan/
   execute scaffold into `WorkflowSpec` rendering (Claude, and OpenAI when the
   task kind is `ARCHITECTURE`/`PLANNING`); `LIGHT_TOUCH` emits a short
   "understand → inspect → edit → verify" list (OpenAI default); `NONE` omits
   the workflow section entirely (small/local families where planning
   scaffolding is a token-budget luxury).
4. **Emit final messages** — always in the existing `InferenceRequest.messages`
   OpenAI wire shape (§0) with `cache_hints` populated for
   `supports_prompt_caching=True` profiles, keeping the stable sections
   (Role, Constraints, Task template) in an identical byte sequence turn over
   turn so Anthropic's existing prompt-cache prefix keeps hitting (§15).

Tool *schemas* are untouched — they remain the existing canonical
OpenAI-function shape translated by adapters (§0). Renderers only produce the
**narrative** tool-usage guidance inside the system prompt (when/when-not
framing), not the JSON Schema itself.

## 12. Context Assembly Pipeline

```text
ContextChunk[]  (existing: retrieval, memory, repo snapshot, working memory)
        │
        ▼
ContextAssembler.assemble()   ← UNCHANGED. Still owns ordering, trimming,
        │                        budget enforcement, CognitiveFirewall
        │                        trust wrapping for repo-derived content.
        ▼
(context_str, ContextAssemblyReport)
        │
        ▼
ContextBuilder.build()   ← NEW. Wraps the above as IRContextNode[], and
        │                   adds two new sources, both marked
        │                   is_instruction_bearing=False (§16):
        │                     • ProjectConventions loader — user's
        │                       CLAUDE.md-equivalent, README, and any
        │                       docs/architecture.md-style file, if present
        │                     • already-classified ProjectType hint
        │                       (velune/repository/project_type.py, existing)
        ▼
PromptIR.context_nodes
```

`ProjectConventions` loading is genuinely new surface (§0 gap 3): a small,
read-only loader that looks for a project's own convention file (mirroring
what Claude Code's own `CLAUDE.md` does for *this* repo, but for the
*user's target* repo Velune is operating on), truncates via the same
`CognitiveFirewall` path already used for repository content, and feeds it in
as one more low-trust, droppable `IRContextNode` — never as a `Role` or
`Constraints` node (§16).

## 14. Failure Modes

| Failure | Behavior |
|---|---|
| Unknown/unregistered `ModelFamily` | Fall back to `GenericProfile` + `GenericRenderer` — same fallback shape already validated by the deleted engine's `StandardAPITemplate` (§0) |
| Required IR section missing (e.g. empty `role`) | Raise loudly in dev/test (mirrors `cognition/prompts`' existing "missing key raises at import-resolve time, never silently empty" contract); in the live turn path, fall back to the task template's baseline role rather than sending an empty system prompt |
| Conflicting constraints (template vs. user request vs. provider default) | Resolved by the single stated precedence (§6): template > user request > provider default — never resolved ad hoc per call site |
| Budget overflow after `TokenOptimizer.fit_to_budget` | Same emergency-drop path `ContextAssembler` already has; `CompilationReport.budget_exceeded=True` is logged, turn proceeds — never crashes |
| Renderer throws (malformed profile, bug in a family-specific renderer) | Circuit-break to `GenericRenderer`, log the exception, never fail the user's turn over a rendering bug |
| `ProjectConventions` file unreadable, absent, or huge | Absent → skip silently (it's optional, unlike `CLAUDE.md` for this repo). Huge/unreadable → same `CognitiveFirewall.wrap_workspace_content` + truncation path already applied to repo content (`prompt_context.py:511-530`) |
| Validator finds an `IRContextNode` attempting to override a `Role`/`Constraints` section from a low-trust source | Rejected outright — see §16, this is a security boundary, not just a quality one |

## 15. Performance Considerations

- `compile_prompt()` must not re-run retrieval; it is a pure downstream
  formatting/ordering pass over already-gathered `ContextChunk[]` — O(sections),
  no additional I/O beyond the new (small, local, optional) `ProjectConventions`
  file read.
- `ProviderProfile` and `TaskTemplate` lookups are plain dicts populated at
  import time (mirrors the already-fast `_baseline`/`_premium` module-level
  dict pattern) — no per-turn parsing.
- Renderer output should be memoized per `(ir_hash, family)` within a single
  turn, since council multi-agent turns may call the compiler once per seat.
- **Prompt-caching alignment is a hard constraint, not a nice-to-have.**
  `InferenceRequest.cache_hints` already exists and Anthropic prompt-caching
  is wired in production. Renderers must keep stable IR sections (Role,
  Constraints, Task template) byte-identical turn over turn so the cached
  prefix keeps hitting; volatile sections (current prompt, freshly retrieved
  context) must render into a segment excluded from the cached prefix. Get
  this wrong and caching silently stops paying off with no visible error.

## 16. Security Considerations

- **The IR must preserve the existing trust boundary.** Repository-derived
  content and the new `ProjectConventions` source are `is_instruction_bearing
  =False` by construction. A renderer wrapping a section in `<constraints>`
  tags or a `## Constraints` header must never do so for content whose
  `IRContextNode.is_instruction_bearing` is `False` — dressing untrusted data
  in instruction-shaped delimiters is exactly the "is this instruction or
  data" ambiguity the Claude research memo names as a quality failure, and
  here it is a prompt-injection vector: a malicious `README.md` or repo file
  must not gain authority just because a renderer's XML/markdown formatting
  makes it *look* like a system instruction.
- `PromptValidator` explicitly rejects any `IRContextNode` that attempts to
  populate a `Role`, `Constraints`, or `OutputContract` slot from a source
  other than the `TaskTemplate` or explicit user request (§14).
- No secrets in IR context nodes — `ProjectConventions` loading reuses the
  existing workspace-content sanitization expectations already established
  for repository logging.
- `ProviderProfile` and `ProviderRenderer` instances are static, reviewed,
  checked-in code — never constructed from user input, network responses, or
  templated strings at runtime. This closes off "prompt injection via a
  malicious provider profile" as an attack surface entirely.

## 17. Future Extensibility

- Adding Groq, Mistral, DeepSeek, Qwen, Ollama, or any future provider is one
  `ProviderProfile` registration (`register_provider_profile`) plus, only if
  its needs aren't covered by `GenericRenderer` + profile tuning, one renderer
  subclass. No compiler, validator, or optimizer changes are required.
- `CompilationReport.ir_hash` + `renderer` id give a stable join key for a
  future evaluation harness to A/B renderer variants per family, feeding into
  the existing observability package (`velune context` / `velune trace`).
- `TaskTemplateRegistry.register()` allows new task kinds to be added by
  future subsystems (e.g. a security-review task kind) without touching the
  compiler.

## 18. Migration Plan

- **Phase 0 lands with zero call-site changes.** The package is pure
  addition; `GenericRenderer` output must be byte-identical to today's
  `ContextAssembler` + `cognition/prompts` output, proven via golden-output
  diff tests (`test_renderers_parity.py`) before anything else proceeds.
- Only after golden-parity is proven does `prompt_context.py` swap its
  final-assembly call to `compile_prompt()`, one surface at a time: REPL
  direct chat first, then council agents, then any future surface.
- The orphaned `velune/cognition/agents/{coder,planner,reviewer}.py`
  duplicate (§0) is explicitly **not** touched by this migration — flagged
  for a separate cleanup task.
- **Blast radius:** touches the call site in `prompt_context.py`, the base
  prompt-resolution step in `cognition/council` agents (once they opt in),
  and `ToolLoopRunner`'s request construction (to pass through
  `cache_hints`/`messages` from `CompiledPrompt` instead of the raw
  assembled string). It does **not** touch provider adapters' wire-format
  translation code, `ContextAssembler`'s internals, `cognition/prompts`'
  baseline/premium resolution, or the tool-schema canonicalization path —
  all of those are consumed unchanged.

## 19. Implementation Phases

1. **IR + data models + folder skeleton** — no behavior change; unit tests
   only exercise construction and validation of dataclasses.
2. **`ContextBuilder` wrapping `ContextAssembler`** — parity tests against
   today's assembled output.
3. **`GenericRenderer` + `TaskTemplateRegistry`** seeded from existing
   `_baseline`/`_premium` content — parity with today's actual system prompts.
4. **`AnthropicRenderer`, `OpenAIRenderer`, `GeminiRenderer`** — opt-in,
   feature-flagged, not yet wired to any live call site.
5. **`PromptValidator`** — conflict/duplicate/overflow/capability-mismatch
   detection, exercised against Phase 3/4 output.
6. **`TokenOptimizer` integration** — cross-section dedup, provider budget
   ceilings, and `cache_hints` alignment verified for the Anthropic renderer.
7. **Cut over the REPL direct-chat path** (`prompt_context.py`) behind a flag,
   with dark-launch comparison logging against the pre-migration output.
8. **Cut over council agents**; retire the flag once stable. Deletion of the
   orphaned `cognition/agents/` duplicate proceeds as a separate, explicitly
   scoped follow-up — not bundled into this phase.
